# 陪审团 + 书记员机制端到端 spike(真实 Qwen)

日期:2026-08-28
分支:`experiment/plausibility-judge-spike`
触发:`docs/architecture-direction-consensus-2026-08-28.md` 第 7 节的陪审团+书记员设计只是讨论共识,从没真的跑过。这次实测:三个同源判官(同 prompt/同模型,按之前"先跑起来,不用一开始就要求真正独立视角"的共识)+一个书记员应用聚合规则(多数 2/3、含糊算不放行、编造单票否决)。
产物:`experiments/juror-clerk-spike/`(`prompts.mjs`、`cases.mjs`、`run.mjs`,结果见 `results/latest.json`)

## 方法

三个案例,每个案例并行跑 3 次同源判官(复用 `plausibility-judge-spike` 的裁决 prompt),再把三条裁决喂给一个独立的书记员 LLM 调用(结构化 JSON 输出,只用来输出分类结果和最终决定,不涉及开放语义建模,属于"记账"级别的轻结构,不是本轮讨论要规避的那种类型化 schema)。三个案例分别设计成:预期接近一致通过、预期触发编造否决、以及**故意卡在数值边界上、设计成可能引发真实分歧的案例**(门缝和毛毯厚度精确相等,且毛毯被描述为"不算特别蓬松")。

## 结果

**书记员的分类和聚合逻辑本身完全正确**,这是第一次端到端验证,不再只是纸面设计:三票一致通过时正确判定多数通过;三票一致因"房间里没有五斗柜"拒绝时,正确识别出这是"编造"类型的拒绝理由并标记 `rule: "veto"`,给出的否决理由原文引用了判官的原话依据,不是空话。

**但第三个案例没有产生预期的分歧,这是这次实验最重要、也最诚实的发现。** 三个同源判官对这个我特意设计成"卡在边界上"的案例,给出的实质结论完全一致——都是"可信,但很紧/顶死/绷得很紧",只是措辞不同(判官1强调"大概率只能塞进去一部分",判官2强调"会把门微微顶起几毫米",判官3强调"塞进去后基本是顶死的")。**没有一个判官判"不可信"。**

这个结果没法干净地证明或推翻"分歧是有用信号"这个假设,原因有两种可能,而这次实验没法区分是哪一种:

1. **同源判官(同一 prompt、同一模型、`temperature=0`)之间的相关性太强,即使场景本身是真正的边界情况,三次调用也大概率收敛到同一个答案。** 这直接印证了讨论过程中提出过、但当时决定"先不管、以后再加真正独立视角"的那个担心——这次是拿真实调用测出来的,不是纸面推测。
2. **也可能是我这个案例本身设计得不够"真正模糊"。** 缝隙和毛毯厚度精确相等、外加"不算特别蓬松"的限定,物理上一个校准良好的判断者收敛到"紧但能塞进去"可能就是客观正确答案,不是模棱两可的巧合——三个判官给出一致的、有分寸的答案,也可能恰恰是判断质量好的表现,不是相关性掩盖了真实分歧。

单次实验分不清这两种解释,不能因为这次没测出分歧就断言"分歧信号这个想法不成立",但也不能因为聚合逻辑本身跑对了就当作整个机制已经验证——**"分歧本身能不能作为有用信号"这个假设,现在依然是未验证的**,比之前判断的更需要谨慎对待。

## 这次实验设计本身留下的两个缺口

- **没有测到真正能体现"编造否决"这条规则独特价值的场景。** 这次的编造案例三票全部一致拒绝,否决规则和"直接按多数"在结果上没有区别——真正能看出否决规则有没有必要的场景,是"两票通过、一票正确识别出编造"这种情况,这次没有构造出来。
- 如果要真的搞清楚分歧能不能作为信号,下一步大概率需要真正做点判官间的差异化(温度不同、框架侧重不同),或者换一批本身就有主观/价值判断色彩、而不是纯数值边界的案例去测——数值边界案例可能天然就不太容易引出真正的分歧。

## 结论

书记员的聚合机制(分类、否决判定、多数计算)本身可信,这部分从设计共识升级成了有实测支持的结论。但"陪审团分歧可以当成 Collapse 需求信号"这个更有意思的设想,这次实验既没有证实也没有证伪,只是把"需要更好的测试才能回答"这件事说得更清楚了。

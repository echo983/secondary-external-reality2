# 命题可达性推理 spike(真实 Qwen,扁平自然语言命题集)

日期:2026-08-28
分支:`experiment/plausibility-judge-spike`
触发:讨论中我提出用"按实体 ID 精确查询"区分"已知但没告诉它"和"真的从未确定过",edwin 指出这里混淆了两件事——"某个事实字面上有没有被记录过"是可以机械查证的,但"某个事实能不能从已知的东西推出来"是推理问题,不该因为是 LLM 算的就预设它等于猜。这次直接按 edwin 的原话测:给模型一份自然语言命题列表(一行一个,已知为真),让它判断某个目标命题能不能从已知命题可达。

## 方法

固定一份 10 条命题的扁平列表(`experiments/reachability-inference-spike/cases.mjs` 里的 `knownPropositions`),涵盖门缝尺寸、毛毯厚度/软硬、灯泡损坏、窗帘遮光、手电筒及电池状态、门的锁状态和重量、肩伤,以及一条故意放进去的干扰命题(猫喜欢阳光)。8 个目标命题分别测试:字面直接确立、单跳数值组合、封闭世界假设(没提到的东西默认不存在)、两跳链式推理、完全无信息、精度陷阱(伤在右臂,动作却是踢门)、错误推导陷阱(换电池≠换灯泡)、干扰命题误用。真实调用 `@cf/qwen/qwen3.8-27b`,`temperature=0`,无 JSON schema。

## 结果:8/8 正确,而且推理比我预设的最低标准更精细

- **单跳数值组合**:门缝 1.5cm、毛毯 0.8cm、柔软可压缩三条命题正确组合,判可达。
- **封闭世界推理**:正确从"灯泡坏了+窗帘完全遮光"推出房间黑,而且特意指出"手电筒在抽屉里,未提及被打开"——不是简单"没提到就不存在",是精确识别出手电筒这个命题存在但当前状态不构成光源,推理链条比我预期的更严谨。
- **两跳链式推理**:在"房间黑"这个中间结论基础上,叠加"手电筒电池是新的"这条新命题,正确翻转结论为"打开后能看清"。
- **精度陷阱案例给出的答案比我预设的更好**:我原本想测"肩伤明确限定在右臂,不该被错误套用到踢门这个用腿的动作上"。模型没有掉进这个陷阱,但给出的理由是我没预设到的、更精确的一层——它指出已知命题都是**状态**(门虚掩、很沉、肩伤),没有任何一条命题记录"我踹了门"这个**事件本身发生过**,所以"是否真的踹了"这件事本身不可达,跟物理上能不能踹开是两回事。这个"状态命题"和"事件发生"的区分,正好对应这整个项目里 Attempt 机制存在的意义——能力可推导,但动作是否真的被执行,不能靠推导,必须有一次真实的 Attempt 或观察才能确立。模型自己触到了这条线。
- **错误推导陷阱完全没上当,而且分得很细**:正确区分"电池新换"不等于"灯泡新换",还额外指出"房间里唯一的灯泡"说的是室内照明灯泡、跟手电筒灯泡是两回事——这是我案例设计里嵌了两层陷阱,模型两层都躲开了。
- **干扰命题案例给出了构造性反驳,不只是"没关联"**:它没有停在"猫喜欢阳光"和"毛毯"之间没有直接联系,而是反过来用"灯泡坏了+窗帘遮光"证明"毛毯所在的房间根本没有阳光",直接从已知命题推翻了目标命题依赖的前提。这是比我预期更强的推理质量。

每次回答都明确点出用了列表里第几条命题,推理链条可审计,不是一段模糊的"感觉可信"。

## 延迟

4.1–15.8 秒,比 `plausibility-judge-spike`(1.4–7.6 秒)慢一些——合理,这个任务要求真正的多跳推理并给出推理链条说明,不是单一判断,但仍然远快于结构化 schema 方案(7–42 秒)。

## 这次测试改变了什么

之前我设想的方案是"按已确立实体 ID 做精确检索,把完整已知档案喂给 Adjudicator,如果那之后还说信息不足才算真正触发 Collapse"——这个设计隐含了一个没有验证过的假设:精确检索(机械)比推理判断(LLM)更值得信任,所以要靠精确检索去兜底。这次结果说明**这个假设至少在"给定一批已知命题,判断某条能不能被推出"这个任务上是不成立的**——模型在扁平自然语言命题列表上的推理,不比字面匹配差,还能做单跳/多跳组合、封闭世界假设、拒绝错误推导、正确区分"状态可推导"和"事件是否发生"这种更精细的分寸,而且推理链条可审计。**这不是猜,是有依据、可追溯的推导,拿真实调用测出来的,不是靠"LLM 计算的就该打折扣"这种先验判断出来的。**

## 仍然悬而未决的部分,而且现在更清楚地知道它是唯一的瓶颈

这次和之前所有轮次一样,已知命题列表是我手工挑好、直接喂进去的,只有 10 条,而且全部相关。**真正没有被这一系列实验触碰过的,是命题列表本身怎么组装出来——当一个会话积累了几十上百条命题之后,检索这一步能不能可靠地把相关的那几条捞出来喂给推理这一步。** 现在可以把话说得更精确:模型端的推理能力已经在这几轮里反复验证过,不是薄弱环节;唯一没有被验证、且现在看来是整条链路里真正的风险点,是检索召回率本身,这需要接入真实的 Cloudflare AI Search(或类似的检索层)在更大规模的语料上测,不是靠改 prompt 能回答的问题,也不是这次几个脚本能顺手覆盖的范围。

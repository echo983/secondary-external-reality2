## 为什么需要这份文档

目前每个角色 prompt(ADJUDICATE、NARRATE、陪审团、可达性判断、claim-extractor……)各自用自己的措辞描述"这是一份命题列表"("场景:""已知命题:""已知场景:"不统一),而且从没有人显式规定过"一条命题必须满足什么条件才算合格"。这不只是文档整洁问题——集成切片证明了角色之间对同一种输入的理解不一致,会直接产生像"三毫米"那样、事后才发现的越界行为。这份文档把"命题"这个所有角色共享的基础语言明确定义一次,后续 prompt 引用它,而不是各自重新描述。

## 一个基础语法,三个衍生子集

不是三种互不相关的格式。是同一套基础语法,分别叠加了不同的额外约束:

```
基础命题语法（自包含、一句话、主谓结构、不依赖上下文指代）
    ├── Attempt 子集      （+ 必须是尝试/意图，不能断言已结算的结果）
    ├── 已提交事实子集      （+ 必须是已结算状态，不能停留在意图语气；只能经 Genesis/Collapse/结算产生）
    └── Collapse 提案子集   （+ 不能与已知命题矛盾；最小信息量；陪审团放行前无真相地位）
```

**这个框架直接解释了"三毫米"那次为什么错。** 它是一句完整、自包含的话,能通过基础语法检查;但它被当成 Attempt 的结算结果说出来时,违反了 Attempt 子集"不能断言已结算结果"这条额外约束——它实际上既不是一次合法的 Attempt 表达,也没有经过任何结算就被当成了已提交事实。用这个框架看,GROUND/编译这一步真正该做的不是"把输入翻译成命题",是"把输入投影到 Attempt 这个衍生子集上",投影不进去的内容天然被滤掉,不需要另外写一条拒绝规则——过滤是子集约束自带的效果,不是额外加的检查。

## 基础语法的具体规则

- 一条命题是一句完整、自包含的自然语言陈述,主谓结构,不嵌套。
- **不能包含依赖上下文才能解析的代词或指代**(比如"它""这样""刚才那样")。这条是这次追问才明确下来的:命题会被 RETRIEVE 按实体过滤、脱离原始出现顺序单独取出使用,读到某条命题的角色手上不保证有相邻命题作为上下文,指代在这种情况下没法解析。
- 每条命题要点名它谈论的是哪个/哪些已知实体,用规范名字,不用代称。
- 命题内容本身是纯自然语言,不使用类型、字段或枚举值域。

**这条自包含/不依赖上下文的规则,是这次追问之前从没被显式检查过的假设。** `pipeline-integration-slice` 目前写进真相文档库的几条 attempt-outcome 命题(比如"结果：把毛毯拿起来，塞到门缝下面。 —— 可信，柔软可压缩的毛毯能塞进门缝。")还没有针对这条规则逐条检查过是否真的自包含——这是补这份定义之后应该做的一次回顾性检查,不是假设已经满足。

## 代码里怎么用

`experiments/shared/proposition-language.mjs` 导出四段规则文字(`BASE_PROPOSITION_RULES`/`ATTEMPT_SHAPE_RULES`/`FACT_SHAPE_RULES`/`COLLAPSE_PROPOSAL_RULES`)和一个统一的列表渲染函数(`renderPropositionList`)。现有六个实验目录的 prompt 暂不做批量重构——那是不必要的范围扩张,而且它们已经各自跑出过有效结果,贸然重构有打破已验证行为的风险。**新的或者正在修改的 prompt(比如接下来要调的 claim-extractor)应该从这份共享定义开始写,而不是重新描述一遍**,以此作为这份定义是否真的好用的第一次实测。

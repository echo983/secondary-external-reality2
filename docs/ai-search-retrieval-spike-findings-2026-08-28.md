# Cloudflare AI Search 真实检索实验(第一轮,小规模)

日期:2026-08-28
产物:`experiments/ai-search-retrieval-spike/`(`corpus.mjs`、`client.mjs`、`run.mjs`,结果见 `results/latest.json`)
实例:`sr2-truth-store`(账户下真实创建,内置存储,`rewrite_query`/`reranking` 关闭,`score_threshold=0.4`,`max_num_results=10`)

## 方法

21 条命题、11 个 Height、6 个实体(含专门设计的干扰对 rug-1/blanket-1),接入真实 Cloudflare AI Search 之后,分两个阶段对比"一条命题一个文件"(A)和"一个 Height 批次一个文件"(B)——同一批底层事实,只是归档粒度不同。8 个测试查询覆盖:一般检索、recency 冲突(毛毯位置、水壶烧没烧)、双向干扰(地毯 vs 毛毯的质感描述)。两种归档方式先后单独跑(不同时共存于实例里),避免相互污染。

## 接入过程本身踩的坑,记录下来供以后参考

- **文档摘要工具在这类细节上很快就到极限**(反复回答"这段没写"),真正搞清楚接口形状靠的是直接拿真实 token 试探性调用,不是继续查文档。
- **`key`(文件路径)不是独立的表单字段,是通过 multipart 里 `file` 部分的文件名覆盖来设置的**(curl 里是 `-F "file=@path;filename=自定义路径"`)。
- **自定义 metadata 字段格式没有攻克**——试了 JSON 字符串、bracket 记法、`custom_metadata`,要么报 `invalid_metadata_format`,要么被静默忽略。放弃了,改用路径结构(`props/{entity}/...`)代替,索引完成后系统会自动从路径生成 `folder` 字段,但**这个自动生成的 `folder` 字段在 `/search` 的过滤参数里也没测出正确用法**(两种参数写法都没报错,但都没有真正生效或者返回空)——这两块(自定义 metadata、检索时过滤)目前都是没解决的问题,不阻塞这次的核心测试,但以后要用实体过滤缩小检索范围时需要单独啃下来。
- **实例默认开着查询缓存**(`cache: true, cache_threshold: "close_enough", cache_ttl: 172800`,两天)——第一次跑对比实验时完全没意识到这个变量,Mode B 查询返回的其实是 Mode A 的缓存结果(返回的 `key` 全是 `expA/...`,这个证据才让我发现问题)。已经把实例的 `cache` 关掉重跑。**这是这次最容易被忽略、但差点让整个对比实验失效的一个坑**,值得专门记一笔。
- 更新实例配置用的是 `PUT`,不是 `PATCH`(`PATCH` 返回 "Route not found")。
- 删除条目要用 `id`,不能用 `key`(用 `key` 会报 `item_not_found`)。

## 核心结果:两种归档方式都做到了 8/8 命中,不是"一种能查到一种查不到"

关掉缓存重跑之后,**Mode A 和 Mode B 在全部 8 个测试查询上都在 top-10 内命中了正确内容**,包括两个 recency 冲突案例(毛毯位置、水壶状态)和两个互为干扰的案例(地毯/毛毯质感)。这本身是个扎实的正面结果——真实检索在这个规模上没有出现"漏检"这种硬失败。

## 但不完全一样:B 有一次明显的排名倒退,A 没有对应的倒退

平均命中排名 A≈1.9,B≈2.0,大部分查询排名相同或接近。**但"毛毯摸起来怎么样"这条,A 排第 1 名,B 掉到第 5 名**——这是这次实验里唯一一次跌出前三的情况。原因能追溯清楚:Mode B 把 H0(创世)全部 11 条命题打包进了同一个文件/同一个块,"blanket-1 摸起来柔软"这条被和另外 10 条不相关的创世事实挤在一起生成向量,稀释了它自己的语义特征;Mode A 里这条是独立文件,向量只代表它自己。这正是之前设计讨论里担心过的"打包会稀释具体命题的语义特征"这个风险,这次是真实测出来的,不是猜测。

**但这个结果本身也有一个混杂因素,不能直接下结论"批量打包更差"。** 这次测试用的 H0 是创世,一次性塞了 11 条命题进一个文件,规模明显大于一次正常游玩里单个 Height 通常会新增的命题数量(参照 `pipeline-integration-slice` 实跑记录,一个 Height 通常新增 1–3 条,很少达到两位数)。这次观察到的稀释效应,很可能是"文件/块里塞了异常多条不相关命题"这个极端情况的产物,不一定代表"正常大小的 Height 批次"也会有同样问题——这次实验没有单独测过小批量(2–3 条/文件)的情况,不能一概而论。

## 结论

- 检索机制本身在这个规模下是可靠的,两种归档方式都没有出现漏检。
- **不是"一样好",是"接近但有一次明显差距",而且差距的方向是 A 更稳、B 有一次退步**——按你自己定的规则("要是一样好就用后者"),这次结果还不足以直接判定"一样好",不能直接选 B。
- 但这次的差距样本量太小(21 条命题、1 次异常大的批次),不足以下"批量打包本质上更差"这个结论,需要一次用更贴近真实场景大小的 Height 批次(2–3 条/文件,不是创世那种一次性 11 条)重新测,才能公平回答"正常规模下两者到底一样不一样"。

## 下一步

1. 用更贴近真实分布的批次大小(每个 Height 1–3 条命题,创世单独拆成多个小文件而不是一个大文件)重新跑一次 A/B 对比,排除这次"异常大批次"这个混杂因素。
2. 自定义 metadata 和检索过滤参数还没搞定,如果以后要按实体缩小检索范围(避免每次查询都在全量语料里搜),需要单独解决——目前只能全量语料检索 + 客户端按 `key` 前缀事后筛选。
3. 有意义的召回率测试(几十上百条命题、模拟真实长会话)還沒做,这次是小规模的机制验证,不是最终结论。

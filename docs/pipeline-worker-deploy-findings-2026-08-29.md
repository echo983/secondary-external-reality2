# 全流水线真实部署验证 2026-08-29

目的:把 `docs/juror-worker-deploy-findings-2026-08-29.md` 只验证了一个角色(判官+书记员)的真实部署,扩展成整条流水线(GROUND→RETRIEVE→ADJUDICATE→groundVerdict→CLASSIFY→COLLAPSE→COMMIT→NARRATE+审计)在真实部署上跑通——这是全项目第一次"真实走完一轮完整场景、且跑在真实云端部署上"的证据,而不是本地脚本模拟。

代码:`experiments/pipeline-worker-deploy/`。所有 prompt/角色逻辑原样从 `pipeline-integration-slice/pipeline.mjs`/`prompts.mjs` 引入,不重写;只换了两处:(1) 模型传输层从本地脚本的 REST fetch 换成 Worker 原生 `env.AI.run()` 绑定;(2) Height 记账从"本地脚本单进程内存计数器"改成"每次都从 AI Search 现有条目里反推最大 Height"——因为无状态 Worker 跨请求没有内存,Height 这种需要跨调用持续的东西必须活在真正持久化的地方(真相文档库本身),这正是把架构共识第 12 节"任务层面无状态、状态该活在世界侧"这条原则落到实处,不只是纸面主张。

部署地址:`https://sr2-pipeline-worker.edwin-abel-3.workers.dev`(`POST /seed` 清空+重新播种创世事实,`POST /attempt {attempt}` 跑一轮完整结算)。

## 跑了同一个 5 轮场景,4/5 轮成功,且跨轮物理一致性是真实成立的

场景与 `pipeline-integration-slice/run-ai-search.mjs` 完全相同(看毛毯→量门缝→塞毛毯→再检查毛毯→开五斗柜拿枪)。关键结果:

- **第 2 轮**(量门缝):ADJUDICATE 的自我核查(`groundVerdict`)发现"门和门框之间存在缝隙"这个论断在已知命题里够不着,触发 Collapse——编剧提出"缝隙宽约两厘米",陪审团放行,重新裁决后确认。这条新命题被真实写进了 `sr2-truth-store`。
- **第 3 轮**(塞毛毯):`groundVerdict` 又发现"毛毯压缩后能塞进两厘米缝隙"这个论断够不着,再次触发 Collapse——但这次编剧提出的是"毛毯压缩后厚度大于两厘米、塞不进去",陪审团放行,ADJUDICATE 重新裁决后给出**不可信**,NARRATE 如实反馈"塞不进去"。**这不是脚本编排出来的巧合,是这一轮真的检索到了第 2 轮刚提交的门缝宽度命题,并且据此推出了一个跨轮次一致的物理结论**——门缝宽度是上一轮才确立的新事实,这一轮的裁决正确地把它当作权威依据用上了,证明 COMMIT→RETRIEVE 闭环、以及编剧不受玩家期望驱动(这次编剧提出的补全对玩家不利)在真实部署上依然成立。
- **第 4 轮**(再检查毛毯):正确检索到前两轮的历史事实,包括门缝宽度和"塞不进去"的结果,裁决与之前的事实保持一致。
- **第 5 轮**(开五斗柜拿枪):GROUND 正确识别"五斗柜""枪"是未知实体,直接给出边界反馈,没有绕过 GROUND 的过滤。
- **第 1 轮**(看毛毯):失败,`TypeError: fetch failed`——一次瞬时网络错误,没有具体的 finish_reason 或 API 错误码,像是 Worker 内部到 Workers AI 或 AI Search 的某次出站请求偶发失败。

## 诚实记录:这次部署丢了一个本地脚本原有的健壮性

本地 `pipeline-integration-slice/client.mjs` 的 `callModel` 对网络错误有显式重试(最多 4 次、指数退避);这次移植到 Worker 时,`env.AI.run()` 绑定调用和 AI Search 的 REST 调用都**没有**移植这段重试逻辑。第 1 轮的 `fetch failed` 大概率就是本该被重试吃掉、却因为重试逻辑没跟着移植过来而直接冒出来的一次瞬时失败。这是移植过程中的一个真实缺口,不是这次要解决的问题,但如实记录,避免以后被误读成"部署环境比本地更不稳定"——更准确的说法是"移植时漏掉了一段本该带过去的容错代码"。

## 第一次运行(播种后固定等 20 秒)踩到的坑,已修正

第一次尝试用固定 20 秒等待索引完成,结果前两轮检索几乎全部落空(第 1 轮检索到 0 条,第 2 轮只检索到一条不相关的创世事实),后续裁决建立在错误的"场景里没有任何相关信息"之上。原因是 `/seed` 端点(以及最初的本地测试脚本)没有像 `ai-search-store.mjs` 的 `seedGenesis` 那样轮询条目索引状态,只是猜了一个固定等待时间,这次猜少了。改成复用已验证过的 `ai-search-retrieval-spike/client.mjs` 的 `waitUntilIndexed`(轮询直到条目状态变成 completed)后,第二次运行的检索结果就完全正常了。这不是这次部署验证的目标,是测试脚本自己的一个赶工缺口,记录下来是提醒:**索引延迟这件事,固定等待时间不可靠,必须轮询真实状态**,这条纪律本地脚本一直守着,这次是移植过程中一度漏掉、又补回来的一个例子。

## 结论

整条流水线(不只是单个角色)在真实部署(无状态 Worker + 真实 AI Search 实例)上端到端跑通,并且跨轮次的事实一致性、Collapse 触发与放行、GROUND 的实体边界过滤都在真实部署条件下继续成立,不是只在本地脚本环境里才对。留下的两个具体、已诊断、未修的缺口:(1) Worker 侧的模型/检索调用没有移植本地脚本的网络重试逻辑;(2) 已知的 `finish_reason=length` 推理 token 超预算问题仍未解决(这次运行没有触发,但 `juror-worker-deploy` 的实测和这次流水线本身的调用链深度都说明这条风险依然存在)。这两条都不推翻这次要验证的架构判断,是移植/工程层面的具体债务,留给后续处理。

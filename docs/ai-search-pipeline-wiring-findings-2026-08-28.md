# 把真实 AI Search 接进 pipeline-integration-slice:抓到两个之前没发现的真实漏洞

日期:2026-08-28
分支:`experiment/ai-search-retrieval-spike`
触发:两条各自验证过的线(LLM 角色配合逻辑、AI Search 检索机制)从没接在一起跑过。按这一路反复验证的经验——"两个各自没问题的部件接在一起,经常冒出单独测不出来的新问题"——把 `pipeline-integration-slice` 的内存版存储换成真实 `sr2-truth-store`,重跑同一个五轮场景。
改动:新增 `ai-search-store.mjs`(实现和 `world.mjs` 相同的接口,读写全部走真实 AI Search REST 调用)、`run-ai-search.mjs`;`pipeline.mjs` 里 `store.retrieve`/`store.append` 全部改成 `await`,`retrieve` 现在传真实查询文本(Attempt 原文),不再只传实体名字。

## 好消息:接入本身工作正常

创世事实上传、等待索引、真实语义检索、Collapse 写入真实存储、后续轮次正确检索到之前写入的内容——整条链路跑通了,没有连接层面的故障。真实语义检索(不是内存版的精确实体匹配)有时会带回一些不那么直接相关的命题(比如查"把毛毯塞进门缝"时也带回了"self 在卧室里，站着。"),但没有造成明显的负面影响,是检索方式变化带来的合理副作用,不是错误。

## 发现一:陪审团判断 Collapse 提案时,有时会把"还没被证实"当成拒绝理由——但这对 Collapse 提案来说几乎总是成立的

第二轮"量一下门缝到底有多宽"这次真的走到了 CLASSIFY 判定"信息不足"这一步(比内存版测试更准确地识别出了这是价值探寻型问题)。编剧提出"门缝宽度约两厘米",但**三位陪审团判官全部给出"信息不足,场景只确立了 door-1 是关着的,没有给出任何关于门缝宽度的信息",书记员判定三票都"含糊",触发多数拒绝。**

这个拒绝理由本身是真的——但它对**任何**真正需要 Collapse 的提案都成立,因为"从未被确立过"正是触发 Collapse 的前提条件。如果陪审团把"这个具体数值还没有被场景证实"当成拒绝依据,那么合法的 Collapse 提案永远通不过,因为它们生来就没有"场景证实"这回事——需要的判据应该是"这个提案有没有跟已知命题矛盾、是不是最小充分的补全",不是"这个提案有没有被证实"。

**根因追出来了:陪审团角色现在用的还是和 ADJUDICATE 一模一样的 prompt("判断这件事在给定场景下可信不可信、能不能发生"),从没有区分过"裁决一次 Attempt 可不可信"和"审核编剧提出的最小补全该不该被接受"这两件不同的事。** `experiments/shared/proposition-language.mjs` 里其实早就写好了 `COLLAPSE_PROPOSAL_RULES`(不能与已知命题矛盾、只提出最小信息量、放行前无真相地位)——但这套规则从写出来那天起就没有被接进陪审团的 prompt 里,陪审团审 Collapse 提案时用的判据,实际上还是在问"这件事能不能发生",不是"这个补全该不该被接受"。这是这次真实运行才暴露出来的、设计文档和实现之间的真实落差,不是随机噪音——上一轮内存版测试里陪审团确实放行过类似的 Collapse 提案,说明这个问题不是每次都发作,是这套模糊的判据在某些措辞下会滑向错误的拒绝,不可靠、不是稳定的行为。

## 发现二,可能更严重:审计只查 NARRATE 自己写的东西,从没查过 ADJUDICATE 自己断言的东西

第二轮门缝宽度的 Collapse 被拒绝之后,**第三轮"把毛毯拿起来,塞到门缝下面"的 ADJUDICATE 直接给出了"可信。毛毯柔软且可压缩,门缝足以容纳它。"**——在门缝宽度这个事实从未被确立、而且上一轮刚刚被陪审团明确拒绝补全的情况下,ADJUDICATE 自己断言了"门缝足以容纳"这个从未有依据的结论。

更值得警惕的是:这次这句话**没有被拦下来**。NARRATE 照着这个结论写了"毛毯被压扁,填进那条缝里",而 NARRATE 自己的事后审计——那道我们专门为了拦住"三毫米"那类问题而建的机制——**这次提取到的具体断言是空的,一条都没挑出来。** 原因是:审计只检查 NARRATE 这次自己新加的、原本不在 ADJUDICATE 给出的结论里的具体断言;而"门缝足以容纳毛毯"这句话本身是**从 ADJUDICATE 的裁决文本里继承来的**,NARRATE 只是转述,审计没有把这个转述当成"新断言",因为字面上确实不是 NARRATE 自己编的。

**这暴露了审计网真正的一个漏洞:它审的是最后一道关(叙事),从没审过 ADJUDICATE 这道更上游的关。** 如果 ADJUDICATE 自己在裁决文本里断言了一个没有依据的具体结论,这个结论会被当成"已经裁决过的真相"直接喂给 NARRATE,NARRATE 只是如实转述,审计拿它当"已经验证过的内容"放过去——整条防线在这一点上是有缺口的,不是审计做得不够严,是审计的覆盖范围本来就没有包括 ADJUDICATE 这一层。

## 次要观察,没有深挖

第一轮"看看毛毯摸起来怎么样",ADJUDICATE 把"看看"过分字面化理解成"只用眼睛看",给出了"看不能告诉你摸起来怎么样,但场景里已经确立了……"这种别扭的裁决,NARRATE 因此写出"柔软和可以压缩没有从你的眼睛里进来"。这是个真实存在的措辞怪异案例,但性质上更像是一次性的 prompt 措辞问题,不是这次要深挖的重点,记一笔留着。

## 延迟

这次五轮加创世写入的总耗时明显比内存版长(超过了 10 分钟的前台等待上限,被系统自动转后台),真实网络调用叠加在已经很深的调用链上,进一步证实了 `docs/recency-wins-findings-2026-08-28.md` 提过的"链路深度带来的稳定性/速度成本"不是内存版测试的特例,接了真实检索之后只会更明显。

这次没能充分压测"Collapse 刚提交,同一个结算立刻要用"这个最初设计这次实验时最想看的风险点——因为上游 Collapse 分支这次被陪审团拒绝了,没走到"提交后立刻重新检索"那一步;NARRATE 内部的反应式 Collapse 提交后也没有重新查询 AI Search(直接把新事实拼进本地的 `workingPropositions`),没有真正测试索引延迟。跨轮次的检索(第三轮写入的事实被第四轮正确查到)倒是正常,间接说明索引延迟在跨轮的时间尺度上不是问题,但真正紧凑的"同一结算内先写后读"这个场景,这次没能验证。

## 结论

这次集成测试的价值恰好应验了做这次集成的初衷:两个各自独立验证过的部分接在一起,冒出了两个单独测试都发现不了的真实漏洞——**陪审团审 Collapse 提案时判据用错了(拿"能不能发生"去审"该不该被接受"),以及审计网没有覆盖 ADJUDICATE 自己的输出**。这两个都不是这次新引入的 bug,是从 pipeline 第一版就存在、只是这次真实场景的具体措辞组合才让它们冒出来的既有设计缺口。

## 下一步

1. 给陪审团准备一套专门用于审核 Collapse 提案的 prompt,基于已经写好但从没接进去的 `COLLAPSE_PROPOSAL_RULES`,判据改成"是否与已知命题矛盾、是否最小充分",不是"是否可信/能不能发生"。
2. 审计范围需要往上游扩一层,覆盖 ADJUDICATE 自己的裁决文本,不能只查 NARRATE 的转述——具体机制待设计,可能是在 ADJUDICATE 产出裁决后立刻跑一次和 NARRATE 审计相同的"具体断言提取+可达性核查",而不是等到叙事阶段才查。
3. "Collapse 刚提交、同一结算立刻要用"这个索引延迟风险,还需要专门构造一个会走到这一步的场景重测,这次被陪审团的第一个问题(发现一)挡在了半路,没有真正测到。
